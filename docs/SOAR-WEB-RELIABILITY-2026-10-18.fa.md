# بررسی اختلال مرورگر Soar — ۱۸ اکتبر ۲۰۲۶

## بازتولید

آزمون با پروفایل ارسالی کاربر، سرور پنل beta9 و موتور واقعی WhiteDNS 1.6.6
انجام شد. مشخصات حساب و لینک‌ها خصوصی نگه داشته شده‌اند. حساب فعال، بدون
محدودیت سرعت و با حجم کافی بود؛ دسترسی مستقیم سرور به Amazon نیز برقرار بود.

| مسیر مرورگر Chrome | example.com | amazon.co.uk |
|---|---|---|
| Soar اولیه، همان تنظیمات خروجی | ERR_CONNECTION_CLOSED، ۴۳٫۱۹ ثانیه | ERR_CONNECTION_CLOSED، ۲۱٫۸۶ ثانیه |
| موتور سازگار MasterDNS با پروفایل ارسالی | HTTP 200، ۲٫۷۵ ثانیه | HTTP 202، ۲۱٫۵۱ ثانیه، صفحهٔ ادامه/بررسی ربات |

موتور مقایسهٔ MasterDNS همان commit پین‌شدهٔ WhiteDNS، یعنی
`74385bc9854d4f4aab9cb7d78dc8c90de75860bd` بود. تنظیمات دستگاه کاربر به‌طور
کامل در دسترس نبود؛ مقایسه با پیش‌فرض‌های WhiteDNS و دو Resolver یکسان انجام شد.
این اعداد رتبه‌بندی عمومی سرعت دو پروژه نیستند.

## علت‌های تأییدشده

۱. قفل‌کردن MaxQName روی ۱۰۱ همراه با دامنهٔ بلندِ هر حساب، تنها حدود ۱۵ بایت
دادهٔ جریان را در بعضی بسته‌ها باقی می‌گذارد. زمان‌بندی چرخشی اولیه، پیام آغاز
چندین TLS را هم‌زمان تکه‌تکه ارسال می‌کرد. در نمونهٔ مستقل از پنل نیز بعضی
مقصدها حدود ۱۰ ثانیه بعد، پیش از تکمیل handshake، اتصال را بستند. بنابراین
قبولی درخواست کوچک HTTPS هنگام اتصال، کیفیت مرورگر را ثابت نمی‌کرد.

۲. موتور پایه پس از چند افت عمومی بسته، اندازهٔ نامِ قبلاً موفق را به حداقل
برمی‌گرداند و برای باقی عمر مسیر دیگر رشد نمی‌داد. آزمون با سقف بزرگ‌تر به‌تنهایی
کافی نبود؛ همین کاهش دائمی در لاگ مسیرها مشاهده شد.

## اصلاح و حدود آن

WhiteDNS 1.6.7-beta2 شروع هم‌زمان جریان‌ها را محدود می‌کند، برای پیام‌های کوچکِ
جریان‌های برقرارشده اولویت دارد و سهم پیشرفت ارسال حجیم را حفظ می‌کند. آزمون
اندازهٔ پرس‌وجو، نام بلند را با نمونهٔ کوتاه مقایسه می‌کند؛ افت مشترک با محدودیت
واقعی اندازه اشتباه گرفته نمی‌شود. محدودیت واقعی با اندازه‌های میانی و تلاش
دوباره پس از مکث کنترل می‌شود. قالب بسته و رمزنگاری Soar تغییر نکرده‌اند و
بردارهای اصلی پروتکل بدون بازتولید گذشتند.

پروفایل خودکار از SafeQName=101 آغاز می‌کند و اجازهٔ یادگیری تا MaxQName=253،
پاسخ تا 1232، سقف درخواست کل 128 و پنجرهٔ هر مسیر 32 را دارد. مقادیر صریح قبلی
بی‌اجازه بازنویسی نمی‌شوند؛ برای استفاده از تنظیم جدید، لینک همان حساب باید
دوباره صادر و وارد اپ شود. تغییر سرور نمی‌تواند موتور نصب‌شدهٔ 1.6.6 را عوض کند.

دو نوبت آزمون مرورگر با نامزد اولیهٔ هستهٔ اصلاح‌شده انجام شد؛ اعداد زیر مربوط به همان نامزد هستند:

| صفحه | نوبت اول | نوبت دوم |
|---|---|---|
| example.com | HTTP 200، ۵٫۰۰ ثانیه | HTTP 200، ۲٫۴۵ ثانیه |
| amazon.co.uk | HTTP 202، ۱۵٫۷۷ ثانیه | HTTP 202، ۵٫۶۰ ثانیه |
| mozilla.org | HTTP 200، ۴٫۲۸ ثانیه، حدود ۵۰ منبع | HTTP 200، ۱۱٫۰۷ ثانیه، حدود ۴۵ منبع |

زمان جدول تا آماده‌شدن DOM است؛ معادل پایان تمام ترافیک پس‌زمینه نیست. در نوبت
اول Mozilla یک درخواست آمارگیری لغوشده بود و در نوبت دوم خطای منبع ثبت نشد.
IP خروجی در نوبت دوم تطبیق داده شد و اعتبار TLS خاموش نشد. پاسخ 202 آمازون
در چند اجرا صفحهٔ بررسی ربات بود و در یک اجرا فقط صفحهٔ واسط دیده شد؛ این
رسیدن پاسخ را ثابت می‌کند، نه بازشدن کامل همهٔ خدمات Amazon. MasterDNS نیز در
آزمون خودکار صفحهٔ بررسی ربات گرفت. تغییر IP خروجی یا حل بررسی سایت، در این
اصلاح انجام نشده است.

تست‌های نگه‌داشته‌شدهٔ Soar، رگرسیون زمان‌بندی/عدالت ارسال، افت مشترک بسته،
فیلتر واقعی طول نام، اندازهٔ میانی، بازیابی پس از رفع محدودیت، قطع یک مسیر DNS
و صحت کامل بدنهٔ TLS بررسی شدند. ساخت رسمی اندروید، آزمون race و واحدهای اپ
در گردش‌کار انتشار اجرا می‌شوند؛ نتیجهٔ انتشار در GitHub قابل مشاهده است.

این بررسی جای تست Full VPN روی گوشی فیزیکی یا شبکهٔ داخل ایران را نمی‌گیرد و
تضمین اتصال روی همهٔ اپراتورها نیست. آن موارد هنوز نیاز به آزمون شبکه/دستگاه
دارند.

منبع اصلی موتور نهایی: [Lantern Soar v0.2.3](https://github.com/getlantern/soar/tree/v0.2.3).
تغییرات WhiteDNS با حفظ مجوز Apache-2.0 در مخزن Android مشخص شده‌اند؛ این یک
نسخهٔ upstream از Lantern نیست.

نامزد نهایی beta2 علاوه بر این اصلاحات، اعلان پنجرهٔ جریان‌های در صف را نیز تا رسیدن نوبت نگه می‌دارد، هم‌زمانی شروع را با ظرفیت مسیر تنظیم می‌کند و اصلاح رسمی بازیابی نشست استفاده‌نشدهٔ Soar v0.2.3 را دارد. نتیجهٔ نهایی آزمون و ساخت رسمی باید جدا از جدول نامزد اولیه خوانده شود.

## ارزیابی نامزد نهایی beta2

در اولین اجرای نهایی، example پاسخ 200 در ۶٫۳۲ ثانیه و Amazon پاسخ واسط 202
در ۱۲٫۹۳ ثانیه داد؛ سپس Mozilla پس از ۳۰ ثانیه با ERR_TIMED_OUT متوقف شد.
لاگ نشان داد چند مسیر DNS پاسخ نمی‌دادند. علت آن رخداد منفرد قطعی نشده است؛
نباید آن را از نتایج حذف کرد یا این نسخه را بدون اختلال نامید.

در اجرای بعدی با ترتیب Mozilla، example و Amazon، هر سه پاسخ گرفتند: به‌ترتیب
200 در ۵٫۶۸ ثانیه، 200 در ۱٫۷۰ ثانیه و 202 در ۸٫۹۵ ثانیه. یک اجرای شش‌صفحه‌ای
دیگر نیز گذشت؛ اما مراجعه‌های تکراری کش مرورگر داشتند و معیار اصلی نیستند.

آزمون نهایی شش‌صفحه‌ای با **بافت تازه و کش خالی برای هر مراجعه** روی یک موتور
پیوسته اجرا شد و IP خروجی نیز تطبیق داده شد:

| صفحه | مراجعهٔ اول | مراجعهٔ دوم با کش خالی |
|---|---|---|
| example.com | HTTP 200، ۱٫۳۹ ثانیه | HTTP 200، ۸٫۹۹ ثانیه |
| amazon.co.uk | HTTP 202، ۱۱٫۷۰ ثانیه | HTTP 200، ۴٫۳۹ ثانیه، صفحهٔ بررسی ربات |
| mozilla.org | HTTP 200، ۱۲٫۰۲ ثانیه، ۴۶ منبع | HTTP 200، ۴٫۱۱ ثانیه، ۴۹ منبع |

در این شش مراجعه خطای منبع ثبت نشد؛ اعتبار TLS فعال بود. عدد 200 آمازون نیز
به‌تنهایی به معنی صفحهٔ فروشگاه نیست: متن صفحه بررسی ربات بود. این نتایج رفع
دو علت بازتولیدشده را پشتیبانی می‌کنند، اما توقف منفرد قبلی، گوشی فیزیکی و
مسیرهای ایران همچنان در حدود اطمینان این انتشار آزمایشی باقی می‌مانند.
