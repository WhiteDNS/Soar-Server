# Cotten TCP timeout investigation — 21 October 2026

One VPS-origin fresh-client HTTPS check previously reached its 12-second overall deadline. The old diagnostic returned a generic tunnel error and `handshake: false` for every HTTPS failure, so that event cannot retrospectively be assigned to tunnel startup, DNS transport, TLS, or the destination. Twelve later instrumented concurrent TCP checks passed before these fixes. A 30-second sample of process-owned DNS TCP connections ranged from 24 to 49, below the unchanged 128-connection listener cap.

The investigation identified and reproduced these independent failure mechanisms:

- Embedded accounts had only two outbound connection workers. Slow destinations could hold both workers while healthy sessions waited in their queues. Each queued attempt then started a fresh connection timeout, allowing queue age plus dialing to exceed a client's deadline. The embedded connection pool now runs eight independent tasks while retaining the previous total of 128 queued tasks and 32 pending admissions per session. The separately sized DNS pool is unchanged.
- Deferred connection work now has an absolute deadline captured at admission. Expired acknowledged SYN requests receive the existing reliable failure packet instead of a new full-length dial or a silent stall. Cancellation on account, stream, or session closure remains quiet. Packet formats and configured limits are unchanged.
- The deferred scheduler could release a stream's worker assignment while more work for that stream was queued. A retry could then overlap an earlier task, and old task cleanup could cancel the newer task. Stream assignments now persist until all queued/running work finishes; task identities and cancellation generations protect retries during stream/session cleanup.
- A synchronous native TCP DNS exchange could time out after consuming part of a response frame. Reusing that connection then interpreted leftover body bytes as a new length prefix and broke the next valid MTU probe. The transport invalidates failed framing and opens a fresh connection for a later exchange, preserving its TCP or TLS dial policy.

The queueing and scheduler changes affect server behavior for existing native clients. The TCP framing repair is included in the bundled native client/probe code; replacing the server does not update installed phone applications. The diagnostic now retains observed tunnel authentication and sanitized failure stages, so future destination or TLS failures can be distinguished from startup failures.

Regression tests simulate encrypted TCP session initialization, stalled destinations, expired queued SYNs, cancellation, fragmented retries, and partial DNS response timeouts. Release verification must include the full Go suites, race checks for changed concurrency paths, native UDP/TCP and SOAR interoperability, a clean pinned-base patch build, and post-deployment tunnel probes.

Deployment replaces executables only. It takes a private stopped-service backup and compares every account's static metadata, all protected settings/key records, configured limits, and service/access configuration. Usage must remain monotonic. Rollback retains the current live database. The original event's exact trigger remains unproven; these reproductions establish concrete timeout mechanisms rather than a unique historical diagnosis.
